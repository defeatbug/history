## 2. 核心问题（答辩高危项）

### 🔴 问题 1：没有真正的后端（最严重）

- Supabase **只用了 `auth`**，没有建任何数据表、没有 migrations、没有 RLS 策略。
- `supabase/functions/` 下只有脚手架 `hello-world`，没有实际业务函数。
- 所有业务数据来自 `src/data/*.ts` 的 mock。
- **学习进度只存在 Pinia 内存中，刷新页面即全部丢失。**

**答辩风险：** 老师必问「你的数据存在哪？换台电脑进度还在吗？」——目前答案是「不在」。

### 🔴 问题 2：API Key 泄露在前端

```ts
// src/services/openai.ts
const apiKey = import.meta.env.VITE_DEEPSEEK_API_KEY
```

`VITE_` 前缀变量会被 Vite 打包进浏览器产物，任何人打开 devtools 即可窃取 Key 并盗刷。

**正确做法：** AI 调用迁移到 Supabase Edge Function，Key 只保存在服务端环境变量。

### 🟠 问题 3：登录形同虚设

- `/login` 页面存在，但 `src/router/index.ts` **没有任何路由守卫**。
- 直接访问 `/stats`、`/friends`、`/pk` 无需登录。
- 好友列表、PK 对手、战绩全部是本地假数据 + 随机数。

### 🟠 问题 4：题型实现不完整

`Question` 接口声明了三种类型：

```ts
type: 'multiple_choice' | 'matching' | 'scenario'
```

但 `LessonDetail.vue` 全部按单选题渲染。数据中已有的 2 道 `matching` 题被错误显示为单选。

### 🟡 问题 5：工程质量缺失

- 无单元测试（无 vitest）
- 无 E2E 测试
- 无 CI/CD
- 死代码：`src/composables/useChat.ts`（无引用）、`src/stores/counter.ts`（脚手架残留）
- 无 `.env` 文件（只有 `.env.example`，且其中可能包含真实 Key 需检查）

## 4. 数据库设计草案

### 4.1 实体关系（ER）概要

```
profiles (用户档案)
  ├─< user_progress      (学习进度，1:1)
  ├─< user_answers       (答题记录，1:N)
  ├─< user_badges        (获得勋章，N:M badges)
  ├─< friends            (好友关系，自关联 N:M)
  └─< pk_matches         (对战记录，1:N)

courses (课程)
  └─< questions          (题目，1:N)

history_events (历史事件)
  └─< event_relations    (事件关联，自关联 N:M)

museums (博物馆)
  └─< artifacts          (文物，1:N)
```

### 4.2 核心表结构草案

```sql
-- 用户档案（扩展 auth.users）
create table profiles (
  id          uuid primary key references auth.users(id) on delete cascade,
  username    text not null,
  avatar      text,
  role        text not null default 'student',  -- student | admin
  created_at  timestamptz default now()
);

-- 课程
create table courses (
  id             uuid primary key default gen_random_uuid(),
  title          text not null,
  description    text,
  period         text,
  civilization   text,
  difficulty     text check (difficulty in ('beginner','intermediate','advanced')),
  estimated_time int,
  cover_image    text,
  sort_order     int default 0,
  created_at     timestamptz default now()
);

-- 题目
create table questions (
  id          uuid primary key default gen_random_uuid(),
  course_id   uuid references courses(id) on delete cascade,
  content     text not null,
  type        text check (type in ('multiple_choice','matching','scenario','fill_blank')),
  options     jsonb,
  answer      jsonb,
  explanation text,
  sort_order  int default 0
);

-- 学习进度
create table user_progress (
  user_id           uuid primary key references profiles(id) on delete cascade,
  completed_lessons uuid[] default '{}',
  total_study_time  int default 0,       -- 分钟
  correct_rate      numeric default 0,
  current_streak    int default 0,
  last_lesson_id    uuid,
  last_position     int default 0,
  updated_at        timestamptz default now()
);

-- 答题记录（含错题本 / 间隔重复字段）
create table user_answers (
  id             uuid primary key default gen_random_uuid(),
  user_id        uuid references profiles(id) on delete cascade,
  question_id    uuid references questions(id) on delete cascade,
  user_answer    jsonb,
  is_correct     boolean not null,
  answered_at    timestamptz default now(),
  -- 间隔重复（SM-2）
  ease_factor    numeric default 2.5,
  interval_days  int default 0,
  repetitions    int default 0,
  next_review_at timestamptz
);

-- 勋章
create table badges (
  id          uuid primary key default gen_random_uuid(),
  name        text not null,
  description text,
  icon        text,
  requirement text
);

create table user_badges (
  user_id    uuid references profiles(id) on delete cascade,
  badge_id   uuid references badges(id) on delete cascade,
  unlocked_at timestamptz default now(),
  primary key (user_id, badge_id)
);

-- 好友关系
create table friends (
  user_id    uuid references profiles(id) on delete cascade,
  friend_id  uuid references profiles(id) on delete cascade,
  status     text default 'accepted',  -- pending | accepted | blocked
  created_at timestamptz default now(),
  primary key (user_id, friend_id)
);

-- PK 对战
create table pk_matches (
  id             uuid primary key default gen_random_uuid(),
  challenger_id  uuid references profiles(id),
  opponent_id    uuid references profiles(id),
  status         text default 'waiting',  -- waiting | in_progress | finished
  challenger_score int default 0,
  opponent_score   int default 0,
  question_ids   uuid[],
  started_at     timestamptz,
  finished_at    timestamptz
);
```

### 4.3 RLS 策略示例

```sql
alter table user_progress enable row level security;

create policy "用户只能查看自己的进度"
  on user_progress for select
  using (auth.uid() = user_id);

create policy "用户只能更新自己的进度"
  on user_progress for update
  using (auth.uid() = user_id);

create policy "用户只能插入自己的进度"
  on user_progress for insert
  with check (auth.uid() = user_id);

-- 课程 / 题目 对所有登录用户只读
alter table courses enable row level security;
create policy "登录用户可读课程"
  on courses for select
  to authenticated
  using (true);
```

## 5. 论文创新点建议

本科毕设想要拿高分，必须有 1 个做深的**创新点**。以下三个方向任选其一：

### 方向 A：RAG 增强的历史知识问答（强烈推荐）

**问题：** 当前 AI 助手是「裸调」DeepSeek，容易编造历史事实（幻觉）。

**方案：**
1. 将项目已有的历史事件库（15 个事件 + 详细讲解）向量化，存入 pgvector
2. 用户提问时先做语义检索，把相关史料作为上下文注入 Prompt
3. 对比评测：裸 LLM vs RAG 增强的事实准确率

**优势：**
- 完美利用项目已有数据
- 是当前热点技术
- 有清晰的实验对比，可量化
- 直接解决历史学习场景的真实痛点

**论文可写：** 向量检索、Prompt 工程、准确率对比实验、消融分析。

### 方向 B：基于间隔重复的个性化复习调度

**问题：** 学生容易遗忘薄弱知识点。

**方案：**
1. 实现 SM-2 / FSRS 间隔重复算法
2. 根据答题历史动态安排复习
3. 统计：使用该算法后知识点留存率提升多少

**优势：** 算法明确，实验设计简单，容易画曲线图。

### 方向 C：基于知识图谱的学习路径推荐

**问题：** 学生不知道该按什么顺序学。

**方案：**
1. 构建历史事件知识图谱（已有 `relatedEvents` 数据）
2. 基于先修关系做拓扑排序 / 图算法推荐路径
3. 对比随机学习的效率

**优势：** 图谱可视化效果好，答辩演示吸睛。

1. **内容表用业务主键（text），用户表用 UUID**

#### 9.3.3 关键设计

**1. 路由守卫与初始化竞态**

认证状态是异步恢复的（`supabase.auth.getSession()`），而路由守卫可能在其完成前执行——
会导致已登录用户被误判为未登录。解决方案：

```ts
// store：幂等初始化，重复调用复用同一个 Promise
let initPromise: Promise<void> | null = null
const init = () => { if (!initPromise) initPromise = doInit(); return initPromise }

// 守卫：先等初始化完成再判断
await userStore.ensureInitialized()
```

**2. 邮箱确认场景的状态机**

开启「邮箱确认」时，`signUp()` 返回 `user` 但 **`session` 为 null**——
用户尚未登录。原代码无条件跳转首页，导致用户以为注册成功却处于未登录状态。

现在区分三态：

| 场景 | session | 处理 |
| :--- | :---: | :--- |
| 注册且关闭邮箱确认 | ✅ | 直接登录，跳转目标页 |
| 注册且开启邮箱确认 | ❌ | **不跳转**，显示「请查收验证邮件」面板 |
| 登录但邮箱未验证 | ❌ | 中文提示 + 一键重发验证邮件 |

**3. 邮件确认链接回跳的自动登录**

用户点邮件里的链接后回到应用（URL 带 `#access_token=...`），
`detectSessionInUrl: true` 会自动解析并触发 `onAuthStateChange`。
登录页通过 `watch(isLoggedIn)` 自动离开，无需手动处理。

**4. 错误码 → 中文映射**

`src/utils/authErrors.ts` 维护错误码词典，并区分三类情况：

- `needsConfirmation` —— 需引导用户去验证邮箱
- `isRateLimited` —— 提示稍后重试
- 未收录错误 —— 原样展示，不丢失信息

对应 Supabase 错误码：`email_not_confirmed` / `invalid_credentials` /
`user_already_exists` / `over_email_send_rate_limit` 等。

#### 9.3.5 测试中发现并修复的 bug：游客刷新被踢出

**现象：** 游客模式下按 F5 刷新，直接被重定向回登录页。

**原因：** 游客身份只存在 Pinia 内存中，刷新后丢失；

初始化时若无 Supabase 会话但标记存在，则恢复游客身份。
同时 `logout()` 区分游客与真实用户（游客无需调用 `signOut` 网络接口）。

> **这个 bug 只有真实浏览器交互测试才能发现** —— 类型检查、构建、
> 静态断言全部会通过。这也是引入 CDP 测试的价值。

#### 9.4.3 Edge Function 的职责

| 职责 | 实现方式 |
| :--- | :--- |
| **鉴权** | 用调用者 JWT 构造客户端，`auth.getUser()` 校验；游客（仅 anon key）返回 401 |
| **限流** | 基于数据库的滑动窗口计数，每 60 秒最多 10 次 |
| **输入清洗** | 丢弃空消息；单条限 4000 字符；请求体限 64 KB |
| **上下文裁剪** | 只保留最近 10 条消息 |
| **用量记录** | 写入 `ai_usage`，供限流与后续统计 |
| **流式透传** | DeepSeek 的 SSE 流直接 pipe 给前端 |
| **错误归一** | 上游 401/402/429/5xx 映射为中文提示 |

#### 9.4.4 关键设计决策

**1. 为什么限流必须用数据库，不能用内存**

Edge Function 是**无状态、多实例**的：每次请求可能落在不同实例上，
内存计数器天然不共享。必须依赖共享存储（PostgreSQL）才能实现可靠限流。

表 `ai_usage` 记录每次调用的时间戳，配合索引
`(user_id, created_at desc)` 与函数 `ai_usage_count()` 完成滑动窗口统计。

**2. 为什么 `verify_jwt = false`**

平台层的 `verify_jwt` 只校验 JWT **签名有效**，而 anon key 本身就是合法 JWT，
因此游客（本应用的游客模式）也能通过。但业务上需要**区分游客与真实用户**
（AI 成本敏感，只对注册用户开放），所以在函数内部用 `auth.getUser()` 自行判定。

**3. 安全通知顺序**

初版代码先检查密钥是否存在、再鉴权，导致未授权的调用者能探测到
「服务端未配置密钥」。已调整为：**先鉴权，后报告配置问题**。

> 这是一个典型的「错误信息泄露服务状态」案例，可作为论文安全设计小节的实例。

**4. 后台任务的正确写法**

用量写入不应阻塞流式响应。使用 `EdgeRuntime.waitUntil()` 把写库任务
交给运行时后台执行，并在不可用时降级为 `await`。

#### 9.5.3 算法实现

**状态量**（与 `user_answers` 表字段一一对应）：

| 字段 | 含义 | 初始值 |
| :--- | :--- | :--- |
| `ease_factor` | 难度系数 EF | 2.5 |
| `interval_days` | 当前复习间隔（天） | 0 |
| `repetitions` | 连续答对次数 n | 0 |
| `next_review_at` | 下次复习时间 | — |

**递推公式**（q 为作答质量 0~5）：

```
若 q >= 3（答对）：
    n = 0  →  I = 1
    n = 1  →  I = 6
    n >= 2 →  I = round(I_prev × EF)
    n ← n + 1
若 q < 3（答错）：
    n ← 0
    I = 1

EF' = EF + (0.1 − (5−q) × (0.08 + (5−q) × 0.02))
EF' = max(1.3, EF')
```

**质量分映射的设计理由：**

本项目只采集到「对 / 错」布尔值，需映射为质量分。选择 **答对 = 4、答错 = 2**：

- **答对取 4 而非满分 5**：代入公式得 `EF' = EF + (0.1 − 1×0.1) = EF`，
  即难度系数保持不变。避免稳定答对的题因连续满分而间隔过度膨胀。
- **答错取 2**：`EF' = EF + (0.1 − 3×0.14) = EF − 0.32`，
  难度系数显著下降，后续复习间隔被拉近。

这样只需「答题正误」就能驱动算法，无需用户额外自评，降低使用摩擦；
若后续要支持自评，只需传入不同的 `Quality` 即可，算法无需修改。

**实测验证的间隔序列**（EF=2.5 连续答对）：

```
1 天 → 6 天 → 15 天 → 38 天 → 95 天
```

#### 9.5.4 关键设计决策

**1. 算法放前端，还是做成数据库函数？**

选择**前端 TypeScript 实现**：

| | 前端 TS（当前选择） | 数据库 PL/pgSQL |
| :--- | :--- | :--- |
| 单元测试 | ✅ 纯函数，29 条用例秒级运行 | ⚠️ 需搭建测试框架 |
| 论文展示 | ✅ 代码清晰，易于讲解与画图 | ❌ 算法淹没在 SQL 中 |
| 换算法（如 FSRS） | ✅ 只改一个文件 | ❌ 需重写存储过程 |
| 防篡改 | ⚠️ 客户端可改自身复习状态 | ✅ 服务端权威 |

复习状态只影响自己的学习节奏，不涉及排行榜/勋章等可获利数据，
篡改风险可接受。**对比**：勋章判定（`evaluate_badges`）就放在服务端，
因为它直接影响成就展示。

**2. 用数据库视图而不是两次查询**

错题本需要同时拿到「答题记录」与「题目内容」。两种做法：

- 前端先查 `user_answers`，再按 id 查 `questions`（两次往返）
- 建立 `wrong_answers_view`（一次往返）

选择**视图**，并用 `security_invoker = true`（PostgreSQL 15+）确保
视图查询走调用者权限，**自动继承 RLS 策略**，不会越权读到他人错题。

**3. 复习队列的双来源**

复习页面支持三种模式：

| 模式 | 含义 | 用途 |
| :--- | :--- | :--- |
| `due` | `next_review_at` 已到期 | SM-2 计划的例行复习 |
| `wrong` | 当前 `is_correct = false` | 错题本主动巩固 |
| `all` | 两者合并 | — |

这么设计是因为：SM-2 失败项的间隔是 1 天，但**刚答错的题应当允许立即重做**
（这也是原算法「失败项当次会话内重做」的意图）。

#### 9.5.6 测试中发现的设计问题

**现象：** 刚答错的题在错题本上看不到「开始复习」入口（因为 `dueCount = 0`）。

> 这暴露了一个常见陷阱：**严格按算法实现不等价于好的用户体验**。
> SM-2 的 1 天间隔是为「下次计划复习」设计的，而用户仍然期待能立即重做错题。

迁移引用了 Supabase 平台提供的 `auth.users` 表与 `auth.uid()` 函数，裸 PG 没有。

它不是迁移，**不会**被 `db push` 推到云端。

其中 `auth.uid()` 从会话变量读取，便于手动模拟不同登录用户来测试 RLS：


### 10.4 磁盘回收备忘

Docker Desktop 在 macOS 上使用稀疏文件 `Docker.raw`，
**`prune` 释放的是虚拟机内部空间，宿主机不一定立刻回收**。

本次实测：Docker 内部清理了 17 GB（构建缓存 8.9 GB + Supabase 镜像 1.7 GB 等），
但宿主机仅回收 1.7 GB。

**真正回收宿主机空间的方法**：
Docker Desktop → Settings → Resources → Advanced → 调小 **Disk image size** → Apply & Restart。

> ⚠️ **不要用 `docker system prune -a --volumes`**：
> 该命令的 `--volumes` 会删除所有未被“运行中”容器占用的卷。
> 当 Docker 刚重启时所有容器都是停止状态，
> 会连带删掉其他项目（如 `titanium-line-api`、`octopus`、`siftory`）的数据库卷。
>
> 安全替代：`docker builder prune -f`（仅构建缓存，无副作用）。
